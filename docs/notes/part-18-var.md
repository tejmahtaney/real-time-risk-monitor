# Part 18 - Value at Risk

## Key maths

All three methods answer "what if this happened right now" — an instant shock with no time decay — and report VaR/ES as positive numbers for losses. Daily vol is always `current simulated vol / √252`.

**Delta-normal.** With δᵢ the dollar delta of underlying i and Σᵢⱼ = ρᵢⱼ·σᵢ·σⱼ the daily covariance, the portfolio's daily P&L is (to first order) normal with standard deviation `sd = √(δᵀΣδ)`. `VaR_α = Φ⁻¹(α)·sd`; the normal expected-shortfall formula `ES_α = sd·φ(Φ⁻¹(α))/(1−α)` gives `ES_97.5 = sd × 2.3378027922014141` exactly (pinned by its own unit test against the prompt's reference value). `Φ⁻¹` is the new `pricing::normal::inv_cdf`, Wichura's AS241 rational approximation — three regimes (a central rational approximation for `|p−0.5| ≤ 0.425`, two tail approximations split at `sqrt(-ln(min(p,1−p))) = 5`), accurate to `1e-13` relative error round-tripped through `cdf`.

**Delta-gamma Monte Carlo.** Draws `r = L·ε` (L the Cholesky factor of the correlation submatrix, ε cached common random numbers from a fixed seed), scales by daily vol, and revalues each of 10,000 scenarios with `Σᵢ [dollar_deltaᵢ·rᵢ + dollar_gamma_1pctᵢ·(rᵢ/0.01)²]`. The second term follows directly from `dollar_gamma_1pct := ½·γ·(0.01·S)²·qty·mult`: for an arbitrary return `r` the same second-order term is `½·γ·S²·r²·qty·mult`, which equals `dollar_gamma_1pct·(r/0.01)²` exactly (dividing by `(0.01·S)²` and multiplying by `(r·S)²` cancels the `S²`, leaving `r²/0.01²`). Common random numbers matter here specifically because two ticks with an unchanged book and unchanged market must report the *same* VaR — without them, two independent 10,000-path runs would differ by sampling noise alone, and the dashboard would look like it was jittering for no reason.

**Historical simulation.** For each date in Part 7's return window (≤99), every calibrated symbol's spot is shocked by `exp(historical log return)` — vol held at today's level (sticky strike) — and the whole book is repriced with `portfolio::value_all`. Each scenario's P&L is measured against an *unshocked* revaluation of the same book at the same time (not the already-computed portfolio total), so a literal zero-return scenario gives exactly `0.0` P&L, tested directly.

**Quantiles.** All three simulation-based paths (MC and historical) use the same linear-interpolation-between-order-statistics definition: index `i = p·(n−1)` (fractional, zero-based), interpolated between `sorted[⌊i⌋]` and `sorted[⌈i⌉]` — NumPy's default, Excel's `PERCENTILE.INC`. ES is the mean of every value at or beyond the interpolated VaR-level threshold, inclusive.

## When each method fails

- **Delta-normal** is blind to convexity. It only sees `δ`, so a position whose delta happens to be small looks safe to it regardless of gamma. The short-ATM-straddle test makes this concrete: with a dividend yield chosen so `r − q + ½σ² = 0` exactly, the call and put deltas cancel to the last bit (`dollar_delta = 0`), and delta-normal reports **`VaR99 = $0`** — while the same book's `dollar_gamma_1pct ≈ −$69` (short options, negative gamma) gives delta-gamma Monte Carlo **`VaR99 ≈ $718`** and historical simulation **`VaR99 ≈ $618`**. A risk desk reading only the delta-normal number would see a flat book; the other two methods see the real risk.
- **Delta-gamma Monte Carlo** is itself only a second-order Taylor approximation — a move large enough that third-order (vanna, volga, true repricing curvature) terms matter will still be mismeasured, just less badly than delta-normal. It is otherwise the most complete of the three at a fixed compute cost, since it prices both delta and gamma without depending on a historical window at all.
- **Historical simulation** is crude at the 99 % level specifically because it has ≤99 points to draw a 99th-percentile order statistic from — one bad or lucky historical day moves the whole figure. It also holds vol fixed at today's level in every scenario (sticky strike), so without a history of *implied* vol it structurally cannot see vega risk: a book whose real danger is an IV collapse, not a price move, looks safer here than it is.

## Design choices

1. **The 1 ms budget decides from a warm-up median, not the first tick.** The very first computed tick always rebuilds the Monte Carlo cache (10,000×n draws), so timing tick 0 alone would trip a sticky throttle on one-off cost, not steady-state cost. `VarCalculator` times the first 20 computed ticks (cache-rebuild time excluded from each sample), then decides once — `N = ⌈median / 1000 µs⌉` clamped to `2..=10`, or `1` (never throttled) if the median is under budget — fixed for the rest of the session. Tested with injected `u64` timings, never wall-clock, including a case where one 5,000,000 µs outlier among 19 cheap samples does not move the decision (the median resists exactly the kind of spike a naive "time the first tick" approach would be fooled by).
2. **The MC path never fully sorts 10,000 losses.** `select_nth_unstable_by` partitions at the 95th-percentile index (the lowest quantile any of VaR95/97.5/99/ES ever needs), then only the tail from that point on is sorted — a few hundred elements, not 10,000. `interpolated_quantile`/`tail_mean_at_or_beyond` keep their plain, fully-sorted-array definitions unchanged; a dedicated test checks the partial-sort path gives bit-identical VaR95/VaR99/ES97.5 to a full `sort_by` over the same fixed-seed losses.
3. **Cholesky is hand-rolled on `Vec<Vec<f64>>`**, not `nalgebra`. `marketdata::simulator` already has a Cholesky-with-shrinkage, but `risk` cannot depend on `marketdata` (CLAUDE.md's dependency direction), and pulling in a linear-algebra crate for matrices of a handful of underlyings is not warranted. `crates/risk/src/var/cholesky.rs` deliberately duplicates the *algorithm* (shrink towards the identity in 0.05 steps until it factorises) — the same trade-off `tune_limits.rs` already makes for `risk::monitor::next_state`.
4. **`pricing` is now a real dependency of `risk`.** Delta-normal calls `normal::{pdf, inv_cdf}` from production code, not just from test scenarios building precise BSM fixtures — Part 9's original "production code never calls `pricing::greeks` directly" scoping no longer holds for this one path.
5. **`config/limits.toml`'s `var_99` is a real, measured ceiling, not a demo trigger.** `tune_limits.rs` now builds a real `VarCalculator` (not a `0.0` placeholder) and records the headline VaR99 across 10 seed-42 sessions: min 5,886, p50 15,163, p90 21,236, p99 24,475, max 24,986. `var_99` is set to 32,500 — about 30 % above the observed peak, in the same "quiet on this sample book, a real ceiling for a bigger move" spirit as `dollar_gamma_1pct`/`vega`/`gross_exposure`, replacing the old, never-evaluated `2,000,000` placeholder.

## Compute times

Measured from a **release build** (`cargo run --release -p server`, i.e. full `-O` optimisations on — a debug build's numbers would say nothing useful about a 1 ms budget), against the real sample portfolio and calibrated five-symbol seed, sampling `GET /api/var` across several live ticks:

| | typical range |
|---|---|
| delta-normal | 3–5 µs |
| delta-gamma Monte Carlo (incl. cache rebuild on the triggering tick) | 215–360 µs |
| historical (≈60-scenario window this run) | 300–500 µs |
| **total** | **530–810 µs** |

Comfortably under the 1 ms budget on this book — `recompute_every_ticks` stayed at `1` for the whole run, so the warm-up throttle never actually engaged here. It exists for a larger book or a slower machine, and is unit-tested independently of whether this particular sample book ever trips it.

## Interview questions

1. **Why does the historical method measure each scenario's P&L against a fresh unshocked revaluation instead of the tick's already-computed portfolio total?** Two numbers that are conceptually "the same" but computed via different code paths can drift apart by floating-point noise or a subtly different filter (e.g. which positions count as active). Repricing the unshocked book with the exact same `value_all` call, valuation time and Active-row filter as every shocked scenario guarantees a zero-return scenario is *exactly* zero, not approximately — which is both a cleaner invariant and a direct, cheap correctness check (tested).
2. **Why is delta-gamma Monte Carlo the default `headline_var_method`, not the historical method?** Historical VaR depends entirely on a single, small (≤99-point) historical window — it is silent about risks the recent past didn't happen to contain, and structurally blind to vega. Delta-gamma MC prices both delta and gamma from the calibrated correlation and current vol, so it generalises better as the headline figure a limit is set against, even though historical simulation remains valuable as a second opinion (shown alongside it in the tile's hover table).
3. **Why does `risk` duplicate `marketdata::simulator`'s Cholesky-with-shrinkage instead of `engine` computing it once and passing the factor down?** `engine` does depend on both crates, so it *could* — but the Monte Carlo cache also needs to regenerate mid-session whenever the active symbol set changes (a position added on a new underlying), which is exactly `VarCalculator`'s own concern, not `Engine::tick`'s. Duplicating a small, self-contained, independently-tested algorithm at the crate boundary keeps that cache-invalidation logic in one place rather than splitting "when to rebuild" (`risk`) from "how to build" (`engine`).
