# Part 11 - Engine and REST API

## The single-owner design, and why it avoids locks

`Engine` holds the clock, the feed, the market state, the book, the P&L attributor and the limit monitor as plain fields, with no `Mutex` or `RwLock` anywhere. Exactly one `tokio` task ever calls a method on it: `Engine::spawn` consumes `self` by value and moves it into the task it spawns, so after that point the only handles left in the rest of the program are `EngineHandle`'s three channel ends. Every other part of the app — every axum request handler, potentially many of them running concurrently — only ever touches `EngineHandle`, never `Engine` itself. Reads go through `watch::Receiver::borrow().clone()`, which is a plain atomic pointer swap under the hood; writes go through an `mpsc` request with a `oneshot` reply, so a command is applied by the one task that owns the state, in whatever order it happens to arrive, with no handler ever blocking on another handler's request. There is nothing to contend for, because there is exactly one place the state can change.

## `watch` versus `broadcast`

`watch::channel` is for *state*: it holds one current value, a new send overwrites the previous one, and a receiver that has been away for ten ticks and finally checks in just sees the tenth value, never the nine in between. That is exactly what a `RiskSnapshot` is — nobody needs the history of snapshots, only the latest one — and it is why `EngineHandle::latest()` never blocks and never queues: there is nothing to queue. `broadcast::channel` is for *events*: every subscriber gets every message in order, and a slow subscriber that falls behind gets an explicit lagged error rather than silently missing values. An `AlertEvent` is exactly the opposite of a snapshot — a client that was disconnected when a limit breached still needs to know a breach happened, not just what the state is now — which is why alerts go out on a `broadcast::Sender<AlertEvent>` instead of being folded into the snapshot's latest-value-only semantics. (The Part 12 WebSocket layer is the actual consumer of `subscribe_alerts`; this part only wires the channel.)

## Design choices worth defending

- **A feed failure freezes prices, not time.** `PriceFeed::step` and `MarketTick::apply_to` both leave their state unchanged on error, so a degraded tick's `MarketState` is provably stale rather than corrupted. But `Engine::tick` still runs settlement, P&L attribution (including the overnight day roll) and limit evaluation every tick regardless, against whatever prices it has. The alternative — freezing the whole pipeline until the feed recovers — would silently stop a `+0d` option from settling at its 16:00 expiry, or an `Overnight` step from rolling the P&L day, for as long as the outage lasted. Only `feed_status` on the resulting snapshot changes.
- **`tick()` is infallible by construction.** Given the rule above, there is no data error `tick()` cannot absorb by marking the snapshot degraded and moving on, so it always returns `Ok`. The `Result` in its signature is kept anyway, matching the prompt exactly and leaving a typed home (`EngineError`) for a future failure class this recovery rule genuinely cannot cover.
- **`Engine<F: PriceFeed>` is generic, not `Box<dyn PriceFeed>`.** `step` runs on the hot path the README's low-latency claim is about, so static dispatch costs nothing in production, where only `Engine<GbmSimulator>` is ever built. The real payoff is in `crates/engine/tests/degraded_feed.rs`: `GbmSimulator` cannot be made to fail on command, so the tests plug in a tiny `FailingFeed` that wraps a real one and fails when told to — impossible to express cheaply behind a fixed concrete type.

## `compute_micros`, one-minute live run

285 samples, polled every 200 ms from `cargo run -p server`'s real `/api/risk-summary` against the five-symbol sample book (`tick_interval_ms = 250`): **median 199 µs, p99 278 µs** (min 167 µs, max 327 µs). A quarter-second tick budget has roughly three orders of magnitude of headroom over the slowest observed tick.

## Interview questions

1. **Why is there no lock anywhere in `Engine`, given many HTTP requests can arrive at once?** Because nothing outside the one task that owns `Engine` ever has a reference to it. Concurrent readers each get their own atomic snapshot of a `watch` channel; concurrent writers each get queued as a message on an `mpsc` channel and applied one at a time by that one task. The absence of a lock is a consequence of the ownership structure, not something bolted on separately.
2. **Why does `AddPosition` reply with a full `PositionRisk` instead of the `Position` it just built?** Every other position-shaped JSON this API returns (`GET /api/positions`) is a `PositionRisk` — the valued, priced form — so replying with anything else would give a client two different shapes for "a position" depending on which endpoint they called. Building it costs one more `PositionBook::value_all` call, which is cheap next to the `compute_micros` numbers above.
3. **What would go wrong if the engine froze its risk pipeline during a feed outage instead of just marking `feed_status: degraded`?** Time would keep moving in the real world but the book would stop noticing: an option scheduled to expire during the outage would never settle, the P&L day would never roll at the close, and theta would stop accruing — all correct-looking numbers that are quietly wrong, discovered only once the feed recovers and everything jumps at once. Running the pipeline on stale prices instead means only the *prices* are wrong, and visibly flagged as such.
