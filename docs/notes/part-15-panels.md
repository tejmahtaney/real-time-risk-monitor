# Part 15 - Dashboard panels

## Key design choices

**Panels are pure prop consumers; one container reads the store.** `Dashboard.tsx` is the only file in the panel tree that calls a `useRiskStore` selector. `PositionsTable`, `RiskTiles`, `AlertsPane` and `Controls` each take plain props and never import `riskStore`. Part 21 re-feeds these same four components from a backtest replay stream instead of the live store, and the only file that would need to change for that is `Dashboard.tsx` (or its Part-21 equivalent) — the panels themselves are agnostic about where their data comes from.

**Positions grouping and sorting are pure functions, not component state derivations.** `lib/positionGroups.ts` exports `groupPositions` and `sortRows` as free functions over `PositionRisk[]`, tested directly with plain fixtures rather than through a mounted table. The group subtotal only sums the six dollar measures plus share delta (meaningful for one underlying, per CLAUDE.md's units section) — there is no `share_gamma` subtotal and no portfolio-level total of either, enforced structurally by the `PositionSubtotal` type simply having no field for it, the same trick `PortfolioTotals` already uses on the Rust side.

**Subtotals sum raw `PositionRisk` fields without re-deriving status rules.** An expired position already has `market_value: 0` and zeroed reporting Greeks from the server (settlement cash paid out); an error position is zeroed too. Summing every row in a group, active or not, is therefore already correct — re-filtering by `status.state` client-side would just duplicate a rule the server already enforces, with a real chance of drifting from it.

**The flash-on-change compares values, not row identity.** `PositionsTable` keeps a `useRef<Map<cellKey, number>>` of every visible numeric cell's last-seen value and, in a `useEffect` keyed on the `positions` array itself (not on any individual field), diffs the new snapshot against it to decide which cells flash and which colour. `prefers-reduced-motion` is handled in CSS (`index.css`), not JS — the flash classes are always applied, and the media query simply turns the animation off, so there is one code path instead of two.

**Add-position validation mirrors `portfolio::spec` exactly, but the server stays authoritative.** `lib/positionForm.ts`'s regexes for `StrikeSpec` (`ATM`, `ATM±N%`, an absolute number) and `ExpirySpec` (`YYYY-MM-DD`, `+Nd` up to 3650) are copied from `crates/portfolio/src/spec.rs`'s `FromStr` impls, not re-derived independently, so the two can't quietly diverge on what counts as well-formed. Client validation only catches obviously malformed input before a round trip; a spec that passes it can still be rejected server-side (a strike that resolves to zero, say), and that `ApiError` is shown inline in the form, per the prompt.

## The Part 14 header staleness fix

Part 14 left an open issue: the header's sim time, session state, clock speed and `compute_micros` all live only on a full `RiskSnapshot`, and neither polling REST route (`/api/risk-summary`, `/api/positions`) returns one, so these fields simply stop updating during an outage with no visual signal that they are frozen. The fix does exactly what the Part 14 note suggested — compares `status` itself, since a snapshot carries no staleness flag of its own: `Header.tsx` now derives `stale = (status === 'polling' || status === 'closed') && snapshot !== null`, greys the four fields (`text-neutral/70`) and shows a small "Stale" badge next to them. It only fires once a snapshot has actually been seen, so the very first `connecting` render (all dashes, nothing frozen yet) stays undecorated. `Dashboard.tsx` applies the same "prefer live, fall back to last known" policy to positions, risk-tile totals/limits and `compute_micros` (using `polledSummary`/`polledPositions` while `status !== 'open'`), for the same reason — today's P&L and the alerts pane have no polling route at all, so they hold their last snapshot value unconditionally, same as the header did before this fix and same as an alerts history naturally would even with one.

## Questions an interviewer might ask

1. **Why does the positions table sort inside each group rather than globally?** Because a portfolio-wide sort by, say, dollar delta would interleave rows from different underlyings under the same header, breaking the grouping the prompt asks for. Each `GroupRows` component calls `sortRows` on just its own `group.rows`, so the chosen column reorders positions within SPY, within AAPL, and so on, independently, while the groups themselves stay in symbol order.
2. **Why is the remembered sort one global `{column, direction}` in `localStorage`, not per group?** The prompt asks to "sort by any column inside each group" as one instruction applied uniformly, and a single remembered state is what the column header UI actually offers — one click target per column, not one per group per column. `loadSortState`/`saveSortState` wrap `window.localStorage` in a try/catch each, so a blocked or full store degrades to "no remembered sort", never a crash.
3. **Why does the alerts pane read `snapshot.active_alerts`/`alert_history` instead of the store's own accumulated `alerts` array?** The store's `alerts` (capped at 200, built from live `alert` WebSocket messages) only starts filling from the moment this client connects, so a page freshly opened mid-session would show an empty history for a while even though breaches already happened. `RiskSnapshot.alert_history` is the engine's own last-200 buffer, present and complete on every tick from the first one this client ever sees, so it has no such gap.
