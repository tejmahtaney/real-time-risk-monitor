# Part 14 - Frontend scaffold and live data hook

## Why the types are generated, not hand-written

Every wire type in this project already lives once, in Rust, with its real field names, its real `Option<T>`s and its real serde tag shape (`#[serde(tag = "type", rename_all = "snake_case")]`, and so on). Hand-writing a parallel TypeScript `interface` for each one creates a second copy of that shape that nothing keeps honest: a field renamed in `PositionRisk`, a new `LimitKind` variant, an `Option` added to `HistoryPoint` — none of these would fail to compile on the frontend, they would just silently produce `undefined` at a field name that used to work, discovered at runtime by whoever is unlucky enough to hit it. `ts-rs`'s `#[derive(TS)]` removes the second copy entirely: the binding is derived from the same struct the server actually serialises, so a breaking change to the Rust type is a breaking change to the generated `.ts` file, caught by `git diff` in the same commit, not a bug report later. `make types` regenerates all 50 files from a `cargo test --workspace export_bindings` run, and they are committed rather than gitignored — a reviewer diffing a PR should see the wire contract change alongside the Rust change that caused it, not have to run a script first to find out.

The one thing this does not do automatically is validate serde's more exotic attributes. `Symbol`, `PositionId`, `StrikeSpec` and `ExpirySpec` use `#[serde(try_from = "String", into = "String")]` to validate on the way in; ts-rs cannot execute `TryFrom`, so left alone it would guess a structural shape from the Rust enum/struct definition underneath — wrong for `ExpirySpec`, which is really always a plain string on the wire (`"+30d"`, `"2026-10-16"`, …), never the tagged union its three variants would otherwise suggest. `#[ts(type = "string")]` on each of those four types overrides the guess with the true wire shape; a real `cargo run -p server` was used to confirm every generated type — including these four and every tagged enum — actually matches the live JSON.

## Why there is one socket per page

`App.tsx` calls `startStream()` from a `useEffect` with no dependencies, and React's development-only StrictMode intentionally mounts an effect, runs its cleanup, and mounts it again — specifically to surface effects that are not idempotent. A `WebSocket` opened directly inside that effect would open two connections to the same backend on every single component mount, which would then need explicit cleanup logic to reconcile. Instead, `src/api/stream.ts` keeps the connection as module-level state behind a `started` flag: the second StrictMode mount calls `startStream()` again, sees `started` is already `true`, and does nothing. There is exactly one socket for the whole page's lifetime, regardless of how many components call `startStream()` or how many times React decides to re-run the effect that does.

## The reconnect strategy

Exponential backoff from 1 s to 30 s, doubling on every failed attempt, with up to 20 % jitter added so that many tabs reconnecting to the same backend after an outage do not all retry in lockstep. The backoff resets back down to 1 s only once a connection has stayed open for 10 s straight (a `setTimeout` armed in `onopen`, cleared in `onclose`) — resetting on the raw `onopen` event instead would mean a server that accepts a connection and immediately drops it (a crash loop, say) gets hammered at the minimum interval instead of backing off.

While the socket is not open, `GET /api/risk-summary` and `GET /api/positions` are polled every 2 s and written into two dedicated store fields (`polledSummary`/`polledPositions`), separate from the live `snapshot`, because neither REST endpoint returns a full `RiskSnapshot` — there is no `sim_time`, `paused` or `compute_micros` to fill in, so the header simply keeps showing its last known values for those during an outage rather than inventing placeholders. Polling stops the instant the socket reopens. On reopening after having seen at least one prior snapshot, `GET /api/history?since=<last seq>` backfills whatever ticks were missed while disconnected, merged into the store's history by `seq` so a server-backfilled point and any client-derived point for the same tick are simply the same entry, not a duplicate.

## Interview questions

1. **Why `zustand` instead of `useState`/Context for the live snapshot?** A `RiskSnapshot` arrives up to several times a second and is read by several independent parts of the shell (the header's sim time, a future risk-tile grid, a future chart). Context re-renders every consumer on every update regardless of which slice they read; `zustand`'s selector hooks (`useConnectionStatus`, `useSnapshot`, `useAlerts`, …) let each component subscribe to exactly the slice it needs, so the connection dot does not re-render every time a new snapshot's Greeks change, and vice versa.
2. **What happens if the backend sends a message type this build of the frontend has never heard of?** `handleMessage` checks `parsed.type` against the known cases in a plain `switch`, over a value typed as `unknown` until narrowed — not a blind cast to the generated `ServerMessage` union — so a new variant falls into the `default` arm, gets `console.warn`ed exactly once per distinct unknown type (via a `Set`), and is otherwise ignored rather than throwing and killing the socket's message loop.
3. **Why does `historyPointFromSnapshot` recompute `worst_limit_utilisation` from `snapshot.limits` instead of trusting a field on the snapshot?** `RiskSnapshot` doesn't carry that figure directly — it is `HistoryPoint`-only, computed server-side in `crates/engine/src/engine.rs` from the same per-tick `limits: Vec<LimitStatus>` the snapshot already exposes. Recomputing it client-side with the identical `Math.max` reduction, rather than inventing a different approximation, is what makes a client-derived history point for a given `seq` bit-for-bit interchangeable with the one a server backfill would return for that same `seq`.
